# 0008 — One binary per repo; ship via `homebrew_casks`

**Scope.** Every CLI in the `jwa-*` family — `jwa-tobrew`, `jwa-harden`, `agentskills`, `prehandover`, and future siblings — lives in **its own GitHub repo** (`jwa91/<name>`) and publishes back to this tap via GoReleaser. This tap repo (`jwa91/homebrew-tap`) keeps no Go source: it only holds the generated `Casks/*.rb` files, exceptional `Formula/*.rb` files, `tap.toml`, ADRs, and tap-management docs. **Distribution kind**: all `jwa-*` CLIs are shipped as **Homebrew Casks** using GoReleaser's `homebrew_casks:` block, not the deprecated `brews:` block — even when the artefact is a CLI binary rather than a `.app` bundle. Modern brew autodetects the cask kind; end-users still run `brew install jwa91/tap/<name>` with no `--cask` flag. **Versioning**: each CLI's tag scheme is plain `vX.Y.Z` in its own repo (no shared namespace, no `cli/v*` prefix); the tap repo's own `vX.Y.Z` tags now version only the tap's structural conventions and never collide with any CLI binary release. **Why.** Three forces converged. (a) Sharing one `v*` tag namespace between the tap's structural CHANGELOG and the `jwa-tobrew` binary's release tag silently double-booked `v0.2.0` (tap-meta tag pointed 10 commits behind the binary we wanted to ship); separating repos eliminates the shared namespace entirely. (b) GoReleaser deprecated `brews:` (homebrew formulae for pre-compiled binaries) in favour of `homebrew_casks:`, matching Homebrew's current prebuilt-binary path; keeping the family on one modern shape removes formula/cask drift. (c) Co-locating publisher (`jwa-tobrew`) and distribution channel (`homebrew-tap`) inside one repo coupled two release pipelines that have no business sharing a CHANGELOG, a tag namespace, or an `.goreleaser.yaml`; pulling the publisher out makes the tap a pure distribution channel and lets `jwa-tobrew` evolve on its own cadence, with `tools/` and the bootstrap `Makefile` going away.
