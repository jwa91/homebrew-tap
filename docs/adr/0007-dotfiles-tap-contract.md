# 0007 — Boundary contract between `homebrew-tap` and `dotfiles`

**Scope.** `~/dotfiles` is upstream of this tap on every axis except binary distribution. **`dotfiles` owns**: the security ground rules at `docs/security-ground-rules.md` (actor classes, 1Password-as-source-of-truth, least-privilege token naming, the `.env.template` + `op run` runtime contract), the canonical `Brewfile` that lists every tap a fresh machine pulls in (including `tap "jwa91/tap"`) plus the items installed from each tap (`brew "jwa-tobrew"`, `brew "jwa-harden"`, `brew "agentskills"`, `brew "prehandover"`), the bootstrap order in `setup/bootstrap.sh`, and any global agent config under `~/.claude`/`~/.codex`/`~/.cursor`. **`homebrew-tap` owns**: only the `Formula/*.rb` and `Casks/*.rb` files (auto-committed by sibling repos' GoReleaser pipelines), the `tap.toml` index, and the tap-level ADRs/docs. The `jwa-tobrew` publisher CLI and its `init`-time scaffold templates now live in `jwa91/jwa-tobrew` (ADR 0008); the project-template scaffolds (the `.env.template` shape, the `.gitignore` rules for `.env*`, the `op run` invocation in `scripts/release.sh`) are embedded in that CLI's binary, not in this repo. **Cross-references are one-way, always tap → dotfiles**: ADRs in this repo cite `~/dotfiles/docs/security-ground-rules.md`; skills (in `agentskills`) reference those same rules when they need to talk about secrets; `dotfiles` never names a path inside the tap repo or imports tap-side conventions back. **Install flows one-way, always dotfiles → tap → projects**: `setup/bootstrap.sh` runs `brew bundle`, which taps `jwa91/tap` and installs the binaries the tap distributes; those binaries (`jwa-tobrew`, `jwa-harden`, `agentskills`, `prehandover`) are then used in projects to scaffold/release/install. The reverse direction — a tap binary mutating `~/dotfiles` — is forbidden. **Forbidden patterns**: (a) the tap or any tap-published project re-declaring its own security model rather than inheriting from `dotfiles`; (b) the tap's `Brewfile`-equivalent — there is none, dotfiles is the only `Brewfile`; (c) `dotfiles` vendoring a binary that exists in the tap (would create two sources of truth for the same install); (d) any tap binary that needs secrets bypassing the `.env.template` + `op run` contract; (e) reference loops where `dotfiles` documents a tap-internal decision. **Why.** Single source of truth per concern. Secrets, identity, and install order are *machine-level* concerns that belong in `dotfiles` because they apply to every project regardless of how it's published; binary distribution is a *publish-channel* concern that belongs in the tap because it applies only to projects that ship installable artifacts. Co-locating them — e.g. a Brewfile in the tap, or a security-rules doc in the tap — would force the rules to be duplicated and inevitably drift (already the failure mode that produced `tap-alignment`). The one-way reference rule (tap → dotfiles) keeps `dotfiles` shippable on a fresh machine with no prior tap state: clone dotfiles, run bootstrap, the tap gets installed as a consequence; the inverse would not terminate. The forbidden-vendoring rule keeps `Brewfile` as the unambiguous "what gets installed on a fresh Mac" manifest, which is the original reason `dotfiles` exists.
